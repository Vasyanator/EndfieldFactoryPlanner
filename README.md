# Endfield Factory Planner (web)

Статичное веб-приложение для планирования завода в игре **Arknights: Endfield**.

Цели проекта:
1. Хранить полный список предметов и строений.
2. Показывать параметры и скорость производства.
3. Рассчитывать цепочки производства.
4. Дать «песочницу» для постройки завода как в игре.

Сейчас реализована основа интерфейса, загрузка данных из локальной папки `data/` и черновой холст планирования.

## Важно для нового ИИ (быстрый ввод в курс дела)

Ключевые факты:
1. Приложение полностью статическое. Никакого backend.
2. Источник данных — корневая папка репозитория: `../data` (относительно `web/`).
3. Браузер читает данные только из `web/public/data` через `fetch('./data/...')`.
4. `web/public/data` не редактируется вручную — она синхронизируется скриптом.
5. Основная архитектура уже разнесена: `App.tsx` — композиция, вкладки — в `src/tabs`, данные — в `src/data`.

Если ИИ нужно «куда-то добавить логику», по умолчанию:
1. Данные/загрузка/вычисления/lookup-таблицы — в `src/data/*`.
2. Экран/вкладка — в `src/tabs/*`.
3. Переиспользуемый UI без доменной логики — в `src/components/*`.
4. Логика планирования (типы/константы/метрики) — в `src/planning/*`.

## Текущий принцип работы (данные)

Приложение полностью статическое:
1. Данные лежат в корневой папке проекта: `../data` (относительно `web/`).
2. Перед запуском dev-сервера и сборкой выполняется скрипт `scripts/sync-data.sh`.
3. Скрипт копирует `../data` → `web/public/data` и генерирует `web/public/data/manifest.json`.
4. В рантайме React читает JSON через `fetch()` из `./data/...`.

Это важно для GitHub Pages и любого статического хостинга: браузер может читать только то, что реально лежит рядом со статикой.

## Актуальная структура проекта

На уровне репозитория:
1. `data/` — исходные данные (JSON + изображения).
2. `data/items/data.json` — список предметов.
3. `data/buildings/data.json` — список строений.
4. `data_editor.py` — настольный редактор данных (источник структуры и визуального стиля плиток).
5. `web/` — фронтенд-приложение (Vite + React + TypeScript).

Внутри `web/`:
1. `web/src/main.tsx` — вход в React-приложение.
2. `web/src/App.tsx` — верхний каркас: хедер, верхние вкладки, композиция экранов.
3. `web/src/styles.css` — все стили приложения.
4. `web/src/components/SectionTabs.tsx` — переиспользуемые табы.
5. `web/src/data/types.ts` — доменные типы (Item, Building включая `type`, TopTab, NodeMetrics и т.д.).
6. `web/src/data/utils.ts` — утилиты: `fetchJson`, нормализация, форматирование, `craftPerSecond`, пути к изображениям.
7. `web/src/data/useGameData.ts` — главный модуль данных (загрузка + вычисляемые структуры).
8. `web/src/tabs/ItemsTab.tsx` — вкладка «Предметы/Строения».
9. `web/src/tabs/items/components/*` — UI-плитки предметов и строений.
10. `web/src/tabs/PlanningTab.tsx` — вкладка «Планирование» (canvas-песочница).
11. `web/src/tabs/ConstructionTab.tsx` — вкладка «Постройка» (пока заглушка).
12. `web/src/planning/types.ts` — типы планирования (узлы/связи/transform).
13. `web/src/planning/constants.ts` — константы холста.
14. `web/src/planning/metrics.ts` — расчёты метрик узлов (потребности/дефицит, распределение потоков).
15. `web/public/data/` — копия данных для браузера (генерируется скриптом).
16. `web/scripts/sync-data.sh` — копирование `../data` и генерация манифеста.
17. `web/vite.config.ts` — конфигурация Vite (включая `base`).

## Как устроен модуль данных (важно)

Точка входа данных — `web/src/data/useGameData.ts`.

Он отвечает за:
1. Загрузку JSON:
   - `./data/items/data.json`
   - `./data/buildings/data.json`
2. Нормализацию и сортировку.
3. Вычисляемые структуры:
   - `itemLookup: Map<string, Item>`
   - `buildingLookup: Map<string, Building>`
   - `buildingItems: Map<string, Item[]>` — какие предметы делает строение
   - `planningBuildings: Building[]` — только фабрики (`is_factory`)
4. Статусы:
   - `loading: boolean`
   - `error: string | null`

Правило: если нужно добавить «загрузка + derived-данные», делай это здесь (или рядом в `src/data/*`).

## Как устроены вкладки

Верхний роутинг — это просто стейт в `App.tsx`:
1. `topTab: 'items' | 'planning' | 'construction'`.
2. При переключении рендерятся соответствующие вкладки.

Распределение ответственности:
1. `App.tsx` — не должен знать деталей плиток, холста и расчётов.
2. `ItemsTab.tsx` — вкладка каталога.
3. `PlanningTab.tsx` — вкладка холста.
4. `ConstructionTab.tsx` — отдельный модуль под будущую логику.

## Планирование: где расчёты

Вкладка планирования (`web/src/tabs/PlanningTab.tsx`) опирается на:
1. `web/src/planning/types.ts` — типы состояния холста.
2. `web/src/planning/constants.ts` — размеры/ограничения масштаба.
3. `web/src/planning/metrics.ts` — расчёт метрик узлов:
   - входящие/исходящие связи,
   - выпуск в секунду,
   - требуемые и обеспеченные ингредиенты,
   - статусы `missing/shortage`,
   - распределение выходов между несколькими входами.

Ключевые особенности планирования:
1. Входы узлов: число входов считается по каждому ингредиенту отдельно, с учётом `batch_size` и лимита `0.5/сек` на вход.
2. Выход одного узла может подключаться к нескольким входам, ресурс распределяется пропорционально спросу.
3. Визуальные статусы ингредиентов:
   - красный: отсутствует (ничего не приходит),
   - жёлтый: недостача (что-то приходит, но меньше нужно).
4. Есть складские узлы:
   - **Выгрузка со склада** — выбирает предмет, даёт `0.5/сек`, только выход.
   - **Загрузка на склад** — принимает `0.5/сек` любого предмета, только вход, можно подключать сколько угодно линий.
5. Есть два складских пула (только для складских узлов):
   - **Потребление** = выгрузка,
   - **Производство** = загрузка.
   В боковых панелях показывается разница (нетто).

Если нужно «сделать расчёт умнее», правильное место — `planning/metrics.ts` и/или `data/useGameData.ts`.

## Что установить

1. Node.js LTS (рекомендуется 20.x или новее).
2. npm (обычно устанавливается вместе с Node.js).

Проверка:

```bash
node -v
npm -v
```

## Запуск в разработке

Из корня репозитория:

```bash
cd web
npm install
npm run dev
```

Что произойдёт:
1. Сработает `predev`.
2. Выполнится `scripts/sync-data.sh`.
3. Данные окажутся в `web/public/data`.
4. Поднимется Vite dev server.

## Проверка типов (рекомендуется для ИИ)

```bash
cd web
npm run check
```

## Сборка

```bash
cd web
npm run build
```

Результат сборки: `web/dist/`.

## Данные и контракты

Текущие точки входа данных:
1. `./data/items/data.json`
2. `./data/buildings/data.json`

Изображения ожидаются рядом:
1. `./data/items/*.png`
2. `./data/buildings/*.png`

`manifest.json` сейчас нужен как служебный артефакт синхронизации и может пригодиться для диагностики и дальнейших экранов.

## Практические правила для нового ИИ

Чтобы не ломать архитектуру:
1. Не возвращай «всё в App.tsx».
2. Новые derived-структуры держи в `src/data/*`.
3. UI-компоненты плиток держи в `src/tabs/<tab>/components/*`.
4. Не меняй пути `./data/...` без понимания синхронизации.
5. После изменений запускай `npm run check` в `web/`.
6. Для планирования используй `planning/metrics.ts` и не дублируй расчёты в UI.
7. Складские узлы — это виртуальные, не из `data/buildings`.

## GitHub Pages / статический хостинг

Базовый сценарий:

```bash
cd web
npm run build
```

Далее публикуется содержимое `web/dist/`.

Важно про `base`:
1. Если сайт будет жить по адресу вида `https://<user>.github.io/<repo>/`, обычно нужно указать в `web/vite.config.ts`:

```ts
base: '/<repo>/'
```

2. Если используется произвольный статический хостинг или просмотр из файлов/подкаталога, часто удобнее оставить:

```ts
base: './'
```

## Что дальше (план развития)

Ближайшие логичные шаги:
1. Вынести состояние и действия холста в отдельный хук `usePlanningState`.
2. Сделать селекторы в `src/data/*` (например, «рецепты по строению», «цепочки»).
3. Вкладка «Постройка»: сетка, размещение строений, проверки производительности.
4. Деплой: добавить GitHub Actions для сборки и публикации на GitHub Pages.
